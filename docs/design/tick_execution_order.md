# Tick実行順序

## 1. 概要

Tick実行順序は、思兼神Coreが固定tickごとに世界状態を更新する際の処理順序である。

思兼神エンジンでは、以下のような多くの要素が1tick内で関係する。

```text
入力
荒魂
禍津
穢れ
観測
偏差
権能候補
祝詞条件
評価
結界Lock
天津裁定
神意
Motion
Battle
Asset
State
言霊Event
因果Log
神託Debug
御魂State
禊Test
View / Renderer
```

これらの順序が曖昧だと、同じ初期状態・同じ入力列・同じSeedでも結果が変わる危険がある。

そのため、思兼神Coreは固定tick内の処理順序を明示的に管理する。

## 2. 最重要原則

```text
同じ初期状態、同じ入力列、同じSeedなら、同じ言霊Event列と因果Logを返す。
```

```text
順序がない世界は事故る。
固定tickと順序の明文化は初期段階で必要。
```

## 3. 推奨Tick実行順序

以下を、将来的な正式順序候補とする。

```text
1. 入力意図収集
2. 外乱生成 荒魂 / 禍津 / 穢れ
3. 観測更新
4. 偏差評価
5. 権能候補収集
6. 祝詞条件判定
7. 候補評価
8. 結界Lock予約
9. 天津裁定
10. 神意確定
11. Motion / Battle / Asset などの処理実行
12. 世界状態反映
13. 言霊Event発行
14. 因果Log記録
15. 神託Debug出力
16. 御魂Stateスナップショット
17. 禊Test不変条件チェック
18. View / Renderer 用の表示状態生成
```

View / Renderer 用の表示状態生成は、表示用データの生成である。
実際の描画処理そのものは天照Renderer側へ渡す。
思兼神Coreは描画を直接担当しない。

## 4. 各段階の責務

### 1. 入力意図収集

猿田彦Inputから入力を受け取り、ゲーム内の操作意図へ変換する段階。

この段階では、まだEntityの位置や状態を直接変更しない。

例:

```text
右へ移動
左へ移動
観測する
祓う
札を置く
```

### 2. 外乱生成 荒魂 / 禍津 / 穢れ

荒魂、禍津、穢れなど、常態を乱す要素を発生・増減させる段階。

例:

```text
穢れが時間経過で増える
荒魂が活発化する
禍津Eventが発生候補になる
```

### 3. 観測更新

Entityや場所が、世界のどの情報を認識しているかを更新する段階。

世界の真実とEntityごとの認識は分ける。
v0.1では、現在Tick、観測者ID、観測位置、感知設定、伝播信号だけを使う純粋関数で、直線距離に基づく感知値を生成できる。
同一観測者の観測を明示的な根拠・反証へ分け、事前確率と観測確信度から信念候補を生成できる。
単一の信念候補を明示閾値と比較し、一時的な警戒意図を生成できる。
根拠・反証の自動分類、信念の採択、永続化、忘却、複数候補の比較、行動選択は行わない。
信号移動、遮蔽、遅延、複数信号の合成を含む観測更新全体はまだ実装しない。

例:

```text
村人は警札を読む
祓師は穢れを読む
獣は匂いを読む
プレイヤーは痕跡を見る
```

### 4. 偏差評価

常態核と現在状態を比較し、偏差を計算する段階。

例:

```text
村の食料偏差
森の穢れ偏差
祠の清浄偏差
治安偏差
```

### 5. 権能候補収集

場所・Asset・Entity・縁・道標・補助Assetなどから、実行可能性のある権能候補を集める段階。

この段階では、まだ実行しない。

### 6. 祝詞条件判定

各権能の使用条件・対象条件・実行者条件を判定する段階。

条件を満たさない権能は候補から外す。

### 7. 候補評価

候補権能が、偏差をどれだけ減らすか、Entityの目的や縁に合うかを評価する段階。

この段階で評価値や理由を残せるようにする。

### 8. 結界Lock予約

複数Entityが同じ対象を同時に操作して状態破綻を起こさないよう、対象Assetや行動枠を予約する段階。

例:

```text
同じ畑を複数人が同時に収穫しない
同じ祠を同時に祓わない
同じ道標を同時に反転しない
```

### 9. 天津裁定

複数候補・複数Entity・複数Assetの競合を解決する段階。

結界Lock、優先度、権限、常態、偏差、危険度などを見て裁定する。

### 10. 神意確定

最終的に、このtickで実行される行動・権能・世界反応を確定する段階。

神意は万能の巨大if文ではなく、候補から選ばれた判断結果である。

### 11. Motion / Battle / Asset などの処理実行

確定した神意に基づき、各サブシステムへ処理を渡す段階。

例:

```text
天鳥船Motion: 移動処理
建御雷Battle: 攻撃・衝突・ダメージ処理
稲荷Asset: Asset状態変化や権能処理
御魂State: 状態更新補助
```

Coreはすべての詳細処理を直接抱え込まない。

### 12. 世界状態反映

各処理の結果を、ゲーム状態・世界状態へ反映する段階。

状態更新は、決定論的で再現可能であることを重視する。

### 13. 言霊Event発行

何が起きたかをEventとして発行する段階。

言霊Eventは「何が起きたか」を流す。

例:

```text
Tick進行
移動発生
衝突発生
ダメージ発生
祓い成功
道標違反
```

### 14. 因果Log記録

なぜ起きたか、何に影響したかを記録する段階。

因果Logは「なぜ起きたか」を残す。

記録候補:

```text
tick番号
対象Entity
検出された偏差
候補権能一覧
候補ごとの評価値
選ばれた神意
発行された言霊Event
変化した世界状態
関連する因果
```

### 15. 神託Debug出力

開発者が判断理由を追えるようにする段階。

出すべきもの:

```text
なぜこの行動を選んだか
なぜ他の行動を捨てたか
どの偏差が効いたか
どの権能が候補にあったか
どの祝詞条件で弾かれたか
どの結界Lockで失敗したか
どの因果が判断に影響したか
```

原則:

```text
世界AIは、説明できないと信用できない。
```

### 16. 御魂Stateスナップショット

必要に応じて、状態保存、リプレイ、ロールバック、デバッグ巻き戻しのためのスナップショットを取る段階。

v0.1では設計候補に留め、実装しない。

### 17. 禊Test不変条件チェック

tick更新後に、不変条件を検証する段階。

例:

```text
EntityId / AssetId が重複しない
存在しないAssetを参照しない
結界Lock中の対象に同時実行しない
偏差計算がNaNにならない
食料やHPなどの値が許容範囲を破らない
神意が候補外の行動を選ばない
祝詞条件を満たさない権能は実行されない
```

### 18. View / Renderer 用の表示状態生成

八咫鏡Viewや天照Rendererへ渡すための、読み取り専用の表示用状態を生成する段階。

Coreは描画そのものを行わない。

## 5. v0.1で実際に扱う範囲

現在のv0.1実装では、まだ上記すべてを扱わない。

現時点で扱っている範囲は以下。

```text
入力意図収集:
  入力 list を受け取る

世界状態反映:
  Tick更新
  プレイヤー左右移動

言霊Event発行:
  Tick進行

終了状態制御:
  終了状態がある場合はTickも位置も変えない

Smoke:
  最小通電確認

因果台帳:
  成功したEntity位置変更結果をTick非減少順で記録

結果再生:
  記録Tickと変更前位置を検証し、位置変更と記録済みEventを再適用

感知値生成:
  伝播信号から直線距離、線形減衰、感度、閾値、確信度を計算
  正常な非感知と契約エラーを分離

信念候補生成:
  明示された根拠・反証観測を同一観測者について集約
  事前確率と観測確信度から決定論的な候補確率を計算

警戒意図生成:
  単一の信念候補を明示的な発生閾値と比較
  閾値以上なら判断層の一時的な派生値を生成

地盤振動警戒経路:
  地盤振動信号から感知値、観測、信念候補、警戒意図を既存APIで順次生成
  非感知、警戒不成立、警戒成立を区別し、ゲーム状態は変更しない
```

v0.1初期では、以下は未実装である。

```text
荒魂
禍津
穢れ
観測更新
信念候補の採択・永続化・忘却
複数信念候補の比較
警戒意図の永続化・ヒステリシス・行動選択
地盤振動信号の発生・移動と複数観測者処理
偏差評価
権能候補収集
祝詞条件判定
候補評価
結界Lock予約
天津裁定
神意確定
異種因果操作の因果台帳記録
因果台帳の永続化
入力・AI・権能・乱数を再実行する完全な記紀Replay
神託Debug
御魂Stateスナップショット
禊Test不変条件チェック
View / Renderer 用表示状態生成
```

## 6. 実装順の候補

Tick実行順序の文書化後、次の実装候補は以下とする。

```text
A. Core基本運動を進める
  - 上下移動
  - 矩形衝突
  - ダメージ
  - 権能Asset最小型

B. 世界AIの土台へ進む
  - 因果Log最小型
  - 神託Debug最小型
  - 偏差最小型
  - 権能候補最小型

C. 箱庭最小モデルへ進む
  - 場所
  - 常態
  - 偏差
  - 穢れ
  - 気配Field
  - 道標Asset
  - NPC反応
```

ただし、一度に全部作らないこと。

## 7. Core肥大化防止

思兼神Coreは中枢であり、雑務係ではない。

Coreが直接抱えない方がよいもの:

```text
実際の描画
入力デバイス処理
カメラ投影
具体的なダメージ計算詳細
ファイルI/O
Assetファイル解析
セーブファイル形式
個別Sceneの中身
デバッグUI表示
```

Coreの責務は以下へ絞る。

```text
固定tickの進行
世界状態の更新順序管理
権能候補の収集
偏差評価
神意による選択
イベントの発行指示
各サブシステムの実行順制御
```

## 8. 決定論

決定論について、以下を原則とする。

```text
同じ初期状態、同じ入力列、同じSeedなら、同じ言霊Event列と因果Logを返す。
```

将来的に乱数を扱う場合、必ずSeed管理を行う。

システム時刻、外部環境、列挙順の不定性、Hash順序などに依存しない。

## 9. 因果台帳再生との関係

`因果台帳再生.再生する` は通常の固定tick更新経路を再実行しない。
入力、AI判断、権能評価、因果操作実行器、乱数消費を迂回して、正式記録されたEntity位置変更結果を検証付きで再適用する。

再生時は仮状態のTickを記録Tickへ進めるが、飛ばしたTickの処理や `Tick進行` Eventを自動生成しない。
Eventは因果台帳に記録された順序のまま再出力し、EventからWorld Truthを再構築しない。
一件でも不整合があれば初期状態へ原子的に戻し、途中状態と途中Eventを公開しない。

この結果再生は完全な記紀Replayではない。
入力列からの再シミュレーション、Snapshot、巻き戻し、任意位置からの再生は後続Phaseとする。
