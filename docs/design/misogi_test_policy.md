# 禊Test方針

## 1. 概要

禊Testは、思兼神エンジンにおける正式な仕様検証方針である。

禊Testは、単なる単体テストではない。
固定tick、決定論、状態遷移、言霊Event列、因果Log、神託Debug、権能ライフサイクル、Asset定義、不変条件を検証するための仕組みである。

禊Testは、思兼神エンジンの設計原則である以下を支える。

```text
壊れない方式を選ぶ
検証を自動化する
未検証箇所を明示する
同じ初期状態、同じ入力列、同じSeedなら、同じ言霊Event列と因果Logを返す
```

## 2. Smoke と 禊Test の違い

```text
Smoke:
  プロジェクトが最低限ビルド・実行できるかを見る通電確認。

禊Test:
  仕様、不変条件、状態遷移、イベント列、因果Log、Asset定義を検証する正式な確認。
```

Smokeの役割:

```text
Coreライブラリを参照できるか
日本語識別子を別プロジェクトから使えるか
最小の状態更新が実行できるか
コンソールで簡単な成功/失敗を確認できるか
```

Smokeでやりすぎないこと:

```text
複雑な仕様検証
多数のケース検証
Asset検証
AI判断検証
権能ライフサイクル検証
因果Log検証
神託Debug検証
衝突やダメージの網羅検証
テストフレームワークの代用品化
```

```text
Smoke = 通電確認
禊Test = 仕様検証
```

## 3. 禊Test の役割

禊Testで扱う対象を以下のように整理する。

```text
Tick更新の不変条件
入力処理の仕様
移動処理の仕様
衝突判定の仕様
ダメージ計算の仕様
権能ライフサイクルの仕様
言霊Event列の検証
因果Logの検証
神託Debugの検証
結界Lockの検証
天津裁定の検証
権能Assetの検証
雛形Assetの検証
派生Assetの解決検証
常態・偏差の検証
```

禊Testは、実装が増えた後に「何となく動いた」ではなく、「仕様として守るべきことが守られている」ことを確認するための基準になる。

## 4. v0.1で検証すること

v0.1では、まず以下を禊Test対象候補として定義する。

```text
初期状態のTickは0
初期状態にプレイヤーEntityが存在する
Tick更新でTickが1増える
Tick更新でTick進行イベントが出る
終了状態ではTickが進まない
終了状態ではイベントが出ない
終了状態では位置が変わらない
入力なしではプレイヤー位置が変わらない
右へ移動でプレイヤーXが+1.0される
左へ移動でプレイヤーXが-1.0される
複数入力は順番に適用される
同じ入力列では同じ結果になる
```

今回、これらのテスト実装はしない。
この文書では、後続作業で禊Testへ移すべき仕様候補として整理する。

未検証のまま実装を増やすと、どこで仕様が崩れたかを追いにくくなる。
ただし、最初からすべてを検証対象にすると実装が止まるため、v0.1ではCoreの最小挙動から始める。

## 6. 不変条件

禊Testでは、以下のような不変条件を重視する。

```text
Tickは通常更新では必ず増加する
終了状態ではTickは増加しない
終了状態では位置も変化しない
同じ初期状態、同じ入力列、同じSeedなら同じ更新結果になる
同じ初期状態、同じ入力列、同じSeedなら同じ言霊Event列と因果Logを返す
言霊Event列は決定論的である
因果Logの記録順は決定論的である
プレイヤーIDが指すEntityが存在する
Entity IDは重複しない
存在しないAssetを参照しない
HPが存在する場合、将来的には負値を許さない
Assetは実行時Stateを持たない
StateはAsset定義を直接改変しない
神意が候補外の行動を選ばない
祝詞条件を満たさない権能は実行されない
結界Lock中の対象に同時実行しない
```

不変条件は、仕様変更時に「変えてよいこと」と「壊してはいけないこと」を分けるための支柱になる。

## 7. 決定論

思兼神Coreの検証では、決定論を重視する。

合言葉:

```text
同じ初期状態、同じ入力列、同じSeedなら、同じ言霊Event列と因果Logを返す。
```

決定論のために避けること:

```text
System.Random を適当に new する
DateTime.Now でゲーム結果を変える
HashSet / Dictionary / Map / Set の列挙順に依存する
並列処理の完了順で結果が変わる
外部ファイルの読み込み順に依存する
候補評価が同点のときに規則なく選ぶ
```

決定論のために行うこと:

```text
乱数Seedを明示管理する
EntityId / AssetId で安定ソートする
Event発行順を固定する
因果Log記録順を固定する
同点評価時のタイブレーク規則を決める
Tick実行順序を固定する
```

## 8. 言霊Event / 因果Log / 神託Debug の検証方針

```text
言霊Event:
  何が起きたかを検証する。

因果Log:
  なぜ起きたか、何に影響したかを検証する。

神託Debug:
  判断理由が追えるかを検証する。
```

初期段階では、因果Log / 神託Debugはまだ実装されていないため、検証方針だけを記載する。

将来的に検証すること:

```text
Event発行後に因果Logが残る
因果Logが発行Eventと対応している
神託Debugに候補権能と選択理由が残る
条件判定で弾かれた理由が神託Debugに残る
結界Lock失敗理由が神託Debugに残る
天津裁定の勝敗理由が神託Debugに残る
```

## 9. 権能ライフサイクルの検証方針

権能ライフサイクルについて、将来的に以下を検証する。

```text
発見された権能だけが候補になる
条件を満たさない権能は候補から外れる
候補評価が決定論的である
結界Lock対象が重複しない
予約失敗時に実行されない
天津裁定で勝った候補だけが実行される
却下された候補には却下理由が残る
実行後に言霊Eventが発行される
実行後に因果Logが残る
神託Debugに判断理由が残る
```

ただし、権能ライフサイクル本体はv0.1初期ではまだ実装しない。
この節は、後続実装時に何を検証対象へ移すかを示す。

## 10. テストフレームワーク導入方針

現時点では、外部NuGet依存を増やさず、Smokeで最小確認を続ける。

ただし、確認項目が増えてきた段階で、正式なテストフレームワーク導入を検討する。

候補:

```text
Expecto
xUnit
FsUnit
```

今回の作業では導入しない。
どれを採用するかも確定しない。

判断基準:

```text
F#との相性
日本語テスト名の扱いやすさ
CLI実行の簡単さ
Codexでの保守しやすさ
外部依存増加の許容度
```

## 11. Smoke肥大化を防ぐ方針

```text
Smokeは通電確認に限定する。
Smokeに仕様検証を増やしすぎない。
仕様検証が増えたら禊Testへ移す。
Smokeは「壊れていないかの入口確認」として維持する。
```

Smokeが巨大化すると、手作りテストフレームワークになってしまうため避ける。

## 14. まとめ

```text
Smoke = 通電確認
禊Test = 仕様検証
```

Smokeは、プロジェクトが最低限ビルド・実行できるかを見る入口確認である。
禊Testは、固定tick、決定論、状態遷移、言霊Event列、因果Log、神託Debug、権能ライフサイクル、Asset定義、不変条件を検証する正式な仕様検証である。

v0.1では、まずCoreの最小挙動を検証対象候補として整理する。
正式なテストフレームワーク導入は、検証項目が増えてから判断する。
