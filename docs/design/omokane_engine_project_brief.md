# 思兼神エンジン企画書

## Project Name

正式名称は「思兼神エンジン」とする。
英数字表記は `OmokaneEngine` とする。

思兼神エンジンは、F#の型、安全な状態遷移、固定tick、決定論的テストを用いて、ゲームルールを日本語で記述・検証するための独自ゲームエンジンである。

## Purpose

最初の目的は、描画や派手なエディタ機能ではなく、描画なしでも検証できる中核ルールエンジンを作ることである。
F#の型システム、判別共用体、レコード、パターンマッチ、単位付き数値、固定tick、決定論的テストを使い、ゲームルールを安全に記述する。

目指すものは次の通り。

- 日本語で読めるゲーム仕様コード
- 型で壊れにくくしたゲームルール
- 描画なしでも進行できるゲーム状態更新
- 固定tickによる決定論的な更新
- イベント分離による描画・音声・UIとの疎結合
- 自動テストで検証できるゲーム仕様
- 将来的にMonoGameなどへ接続できる構造

## Design Philosophy

思兼神エンジンは、曖昧な数値や暗黙の状態に頼らず、状態、入力、イベント、結果を明示的な型として表す。
ゲームの進行は固定tickを基本とし、同じ初期状態、同じ入力列、同じシードなら同じ結果になることを重視する。

数値は直接散らさず、速度、距離、時間、判定幅、反応猶予などの関係から導出する。
残った数値には、なぜその値なのかを仕様またはコメントに残す。

描画、音声、UIはゲームルールから分離する。
Coreは演出を直接実行せず、イベントとして返す。

思兼神エンジンでは、NPCだけでなく、世界・場所・施設・Asset・勢力・環境そのものが状態を持ち、変化に反応し、秩序や機能を保とうとする。
この思想を「世界そのものがAIになる」と表現する。
その中核概念として、常態核・偏差・復帰行動・常態収束機を扱う。
詳細は `docs/design/jotai_convergence_machine_spec.md` を正とする。

## Japanese API Policy

F#の型名、関数名、判別共用体、レコードフィールドには日本語を使ってよい。
ゲーム仕様上の概念は日本語で表し、後から読んだときに仕様として理解できる名前を優先する。

F#予約語、外部ライブラリAPI、CLIツール名、フォルダ名、プロジェクトファイル名は英語または英数字のままでよい。
フォルダ名やプロジェクト名は、互換性と保守性のため英数字を優先する。

## Subsystem Names

ゲームエンジン本体のサブシステム名は次の通り。

- `思兼神Core`: 判断・状態・固定tick・イベント統括
- `天照Renderer`: 描画・光・画面出力
- `建御雷Battle`: 戦闘・攻撃・衝突・ダメージ
- `猿田彦Input`: 入力・操作・案内
- `天鳥船Motion`: 移動・速度・座標・物理もどき
- `八咫鏡View`: カメラ・表示変換・座標投影
- `天岩戸Scene`: シーン遷移・画面状態
- `稲荷Asset`: アセット・リソース管理
- `言霊Event`: イベント・通知・ログ
- `御魂State`: セーブ・復元・状態保存
- `禊Test`: 検証・テスト・不変条件チェック

## v0.1 Goal

v0.1では `思兼神Core` の最小実装を目標とする。
題材は固定tick避けゲーのような、描画なしでも進行と検証ができる小さな仕様を想定する。

v0.1で扱う候補は次の通り。

- 固定tick更新
- 入力型
- 位置・速度・時間の型
- プレイヤー状態
- 敵弾または簡易エンティティ
- 当たり判定
- ゲームオーバー判定
- イベント出力
- 決定論的な更新
- 最小テスト

## First Core

最初に作るべき中核は、入力一覧と現在のゲーム状態から、次のゲーム状態とゲームイベント一覧を返す純粋な更新処理である。

```text
入力一覧 + 現在のゲーム状態
          ↓
      ゲーム更新
          ↓
次のゲーム状態 + ゲームイベント一覧
```

この中核は描画に依存しない。
Renderer、UI、音声、ログは、Coreが返すイベントを読み取って処理する。

## Out of Initial Scope

最初から作らないものは次の通り。

- UnityやUnrealのような全部入りエンジン
- 3Dエディタやノードエディタ
- 高度な物理エンジン
- 巨大なアセット管理ツール
- 先行したプラグイン機構
- 描画前提のゲーム進行

## Codex Operation Policy

Codexは、既存ファイルを確認してから変更する。
ゲームエンジン本体、ゲームルール、固定tick更新、入力処理、当たり判定、既存テストの意味を不用意に変更しない。

依存追加、project file変更、lockfile変更、install系コマンド実行が必要になった場合は、事前に理由と差分を報告する。
外部依存パッケージを勝手に追加しない。

## Run Report Policy

Codex作業完了時は、既存のRun Report機構を使って `docs/codex/runs/latest.md` を更新する。
個別Run Reportは `docs/codex/runs/YYYY-MM-DD_HHMM_<slug>.md` に保存する。

Run Reportの見出しはASCII英語固定にする。
本文には日本語を含めてよい。
スクリーンショット共有を前提にせず、Markdown本文を他チャットへ共有できる状態にする。

作業完了時はクリップボード送信を必ず試行する。
ただし、クリップボード送信成功は作業完了条件にしない。
`latest.md` が保存されUTF-8で読めるなら最低限成功とする。
