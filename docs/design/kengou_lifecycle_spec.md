# 権能ライフサイクル仕様

## 1. 概要

権能ライフサイクルは、思兼神エンジンにおいて、権能が発見され、条件判定され、評価され、予約され、裁定され、実行され、結果として世界状態・言霊Event・因果Log・神託Debugへ反映されるまでの流れである。

権能は、単なる関数呼び出しではない。

```text
権能 = 世界やAssetがEntityへ提示する行動可能性
```

そのため、権能は実行前に以下を通過する。

```text
誰が見つけたのか
使える条件を満たすのか
どの偏差に反応しているのか
他Entityと競合していないか
実行後に何が起きるのか
なぜ選ばれたのか
```

## 2. Tick実行順序との関係

権能ライフサイクルは、固定tick実行順序の中に組み込まれる。

推奨位置は以下。

```text
入力意図収集
外乱生成
観測更新
偏差評価
権能候補収集
祝詞条件判定
候補評価
結界Lock予約
天津裁定
神意確定
Motion / Battle / Asset などの処理実行
世界状態反映
言霊Event発行
因果Log記録
神託Debug出力
```

権能ライフサイクルは、上記のうち以下の中核部分を担当する。

```text
権能候補収集
祝詞条件判定
候補評価
結界Lock予約
天津裁定
神意確定
実行
結果反映
言霊Event発行
因果Log記録
神託Debug出力
```

Tick実行順序全体については `docs/design/tick_execution_order.md` を正とする。
この文書は、その中の権能に関する流れだけを詳細化する。

## 3. 基本ライフサイクル

以下を基本ライフサイクルとして定義する。

```text
1. 発見
2. 条件判定
3. 評価
4. 予約
5. 裁定
6. 実行
7. 結果反映
8. 言霊Event発行
9. 因果Log記録
10. 神託Debug出力
```

## 4. 各段階の責務

### 1. 発見

Entityが、場所・Asset・縁・観測・道標・補助Assetなどから権能候補を見つける段階。

例:

```text
村人Entityが畑Assetの「収穫する」を発見する
村人Entityが祠Assetの「祈る」を発見する
プレイヤーが道標Assetの「読む」を発見する
祓師Entityが穢れFieldから「祓う」を発見する
```

この段階では、まだ権能を実行しない。
候補として列挙するだけである。

発見に影響するもの:

```text
Entityの位置
観測範囲
読解能力
縁
道標Asset
気配Field
場所記憶Asset
補助Asset群
```

### 2. 条件判定

祝詞により、権能が実行可能かを判定する段階。

判定対象:

```text
実行者条件
対象条件
必要な観測
必要な縁
必要な資源
対象の状態
場所の状態
世界状態
結界Lockの有無
```

条件を満たさない権能は候補から外す。

例:

```text
畑が成熟していないため「収穫する」は不可
祠に穢れがないため「祓う」は不可
通行許可がないため「神域に入る」は不可
対象が遠すぎるため「攻撃する」は不可
```

条件判定で弾かれた理由は、将来的に神託Debugへ残す。

### 3. 評価

条件を満たした権能候補を評価する段階。

評価観点:

```text
どの偏差をどれだけ減らすか
実行者の常態・欲求・目的に合うか
対象との縁に合うか
危険度はどれくらいか
必要コストはどれくらいか
失敗時の副作用は大きいか
他候補より優先する理由があるか
```

例:

```text
村の食料偏差が高いため「収穫する」の評価が高い
祠の穢れ偏差が高いため「祓う」の評価が高い
魔物接近中のため「逃げる」の評価が高い
対象との縁が強いため「助ける」の評価が高い
```

評価値だけでなく、評価理由も残せるようにする。

### 4. 予約

結界Lockにより、対象Assetや行動枠を予約する段階。

予約の目的は、同じ対象に対する同時実行による状態破綻を防ぐことである。

例:

```text
同じ畑を複数人が同時に収穫しない
同じ祠を複数人が同時に祓わない
同じ宝箱を複数Entityが同時に開けない
同じ道標を同時に修復・破壊・反転しない
```

予約対象候補:

```text
対象Entity
対象Asset
場所
行動枠
道標Asset
気配Fieldの発生源
倉庫や資源スロット
```

予約に失敗した場合、その権能は実行候補から外れるか、次tickへ再試行する。

### 5. 裁定

複数候補・複数Entity・複数Assetの競合を天津裁定で解決する段階。

裁定が必要な例:

```text
村人Aと村人Bが同じ畑を収穫したい
雨が火を消したいが、炎が家を燃やしたい
祈祷が穢れを祓いたいが、禍津Eventが穢れを増やしたい
兵士が門を閉じたいが、商人が通りたい
村の常態と森の常態が衝突する
```

裁定の入力:

```text
候補権能
評価値
優先度
権限
縁
常態核
偏差
危険度
結界Lock状態
因果履歴
```

裁定の出力:

```text
採用された候補
却下された候補
却下理由
競合結果
```

### 6. 実行

裁定を通過した権能を実行する段階。

Coreはすべての詳細処理を直接抱え込まない。

処理の委譲先例:

```text
天鳥船Motion:
  移動、速度、座標変更

建御雷Battle:
  攻撃、衝突、ダメージ

稲荷Asset:
  Asset状態変化、権能処理、Asset参照

御魂State:
  状態保存・復元に関わる処理

言霊Event:
  発行予定Eventの受け取り

因果Log:
  記録予定の原因情報
```

権能Assetは任意コードを実行しない。
実行できる処理は、エンジン側が定義した安全な権能と各サブシステムの処理に限定する。

### 7. 結果反映

実行結果を世界状態へ反映する段階。

例:

```text
食料が増える
穢れが減る
HPが減る
Entityが生成される
対象が削除される
道標が修復される
気配Fieldが変化する
場所記憶Assetが更新される
```

結果反映は決定論的である必要がある。

### 8. 言霊Event発行

何が起きたかを言霊Eventとして発行する段階。

言霊Eventは「何が起きたか」を流す。

例:

```text
権能発見
権能条件失敗
権能予約成功
権能予約失敗
権能裁定成功
権能実行
祓い成功
収穫成功
道標違反
対象削除
Entity生成
```

v0.1では、すべてを即実装しない。
まずは将来候補として定義する。

### 9. 因果Log記録

なぜ起きたか、何に影響したかを因果Logへ記録する段階。

因果Logは「なぜ起きたか」を残す。

記録候補:

```text
tick番号
実行者Entity
対象Entity / Asset
使用された権能
反応した偏差
参照した常態核
評価値
裁定結果
発行された言霊Event
変化した世界状態
関連する因果
```

例:

```text
村人が祠で祈った理由:
- 村の穢れ偏差が高い
- 祠に「祈る」権能がある
- 村人は祠を観測済み
- 村人と祠に縁がある
- 畑の収穫より祈祷の優先度が高かった
- 神意が祈祷を選んだ
```

### 10. 神託Debug出力

開発者が判断理由を追えるようにする段階。

出力候補:

```text
なぜこの権能を選んだか
なぜ他候補を捨てたか
どの偏差が効いたか
どの権能が候補にあったか
どの祝詞条件で弾かれたか
どの結界Lockで失敗したか
どの因果が判断に影響したか
どの裁定規則で勝敗が決まったか
```

原則:

```text
世界AIは、説明できないと信用できない。
```

## 6. 権能タグとの関係

権能タグは、権能名そのものではなく、複数権能に共通する性質を表す。

権能ライフサイクルでは、権能タグを主に以下で使う。

```text
候補の分類
UI表示
デバッグ表示
AI候補の粗い絞り込み
禊Testでの分類
```

ただし、権能タグだけで判断を完結させない。

例:

```text
攻撃系 だから必ず敵対行動として実行する
AI選択可能 だから必ず候補に入れる
```

このような単純化は避ける。

タグは分類棚であり、判断本体ではない。

権能タグ全体については `docs/design/kengou_tag_design.md` を参照する。

## 7. 神意との関係

神意は、候補から選ばれた判断結果である。

神意を万能の巨大if文にしない。

推奨スコープ:

```text
Entity神意
場所神意
村神意
勢力神意
世界神意
```

例:

```text
村神意:
  食料偏差を減らす

村人Entity神意:
  畑で収穫する

畑Asset神意:
  収穫権能を許可する

建御雷Battle神意:
  攻撃を命中として処理する
```

神意を一枚岩にすると、AIがすべてを決め、プレイヤーやEntityがただの駒になる危険がある。

## 8. 失敗の扱い

権能は、ライフサイクルの各段階で失敗しうる。

失敗例:

```text
発見できない
観測していない
条件を満たさない
資源が足りない
対象が存在しない
対象が結界Lock中
裁定で負ける
実行中に対象状態が変わる
副作用で別の偏差が発生する
```

失敗は単なるエラーではない。

思兼神エンジンでは、失敗も世界の出来事として扱う。

例:

```text
祓いに失敗した
↓
穢れが少し増える
↓
因果Logに失敗理由が残る
↓
神託Debugに条件不足が出る
```

ただし、プログラム上の不正状態と、ゲーム内の失敗は分ける。

```text
ゲーム内失敗:
  条件不足、資源不足、裁定負け

プログラム不正:
  存在しないEntity参照
  重複ID
  NaN
  不正なAsset参照
```

## 9. 決定論

以下を原則とする。

```text
同じ初期状態、同じ入力列、同じSeedなら、同じ言霊Event列と因果Logを返す。
```

権能ライフサイクルでは、特に以下に注意する。

```text
候補権能の並び順を固定する
EntityId / AssetId で安定ソートする
同点評価時のタイブレーク規則を決める
結界Lock予約順を固定する
裁定順を固定する
言霊Event発行順を固定する
因果Log記録順を固定する
Set / Map / Dictionary の列挙順に依存しない
```

将来的な実装段階は以下を候補にする。

```text

  候補収集と条件判定を追加する
```

## 13. まとめ

```text
世界が権能を提示し、存在がそれを選ぶ。
```

権能ライフサイクルは、この思想を固定tick上で決定論的に扱うための手順である。

権能は、発見された瞬間に実行されるものではない。
条件判定、評価、予約、裁定を通り、選ばれたものだけが実行される。

この段階化により、同じ畑を複数Entityが同時に収穫する、祈祷と禍津Eventが矛盾して穢れを操作する、雨と炎が同じ対象を不安定に更新する、といった状態破綻を防ぐ。

最初から全部を作らず、まずは権能Id、名前、タグ、発行Event程度の最小型から始める。
