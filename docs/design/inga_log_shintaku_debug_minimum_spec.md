# 因果Log / 神託Debug最小型設計

## 1. 概要

因果Logと神託Debugは、思兼神エンジンの世界AI判断を説明可能にするための仕組みである。

言霊Eventは「何が起きたか」を流す。
因果Logは「なぜ起きたか」を残す。
神託Debugは「なぜその判断を選んだか」を開発者に見せる。

この文書で使用する「因果Log」は、現行の日本語APIでは「因果台帳」に対応する。
文書全体の旧称は維持するが、実装上の正式履歴は `因果台帳` と呼ぶ。

原則:

```text
世界AIは、説明できないと信用できない。
```

## 2. 言霊Event / 因果Log / 神託Debug の違い

```text
言霊Event:
  ゲーム内で起きた出来事の通知。
  例: Tick進行、移動発生、衝突発生、祓い成功、道標違反。

因果Log:
  出来事がなぜ起きたか、何に影響したかを残す履歴。
  例: 穢れ偏差が高かったため祓いが選ばれた。

神託Debug:
  開発者が判断過程を追うための説明情報。
  例: 候補権能、評価値、却下理由、裁定理由、Lock失敗理由。
```

言霊Eventはゲームプレイやシステム連携に使う。
因果Logは履歴、リプレイ、物語、デバッグ、AI判断に使う。
神託Debugは開発時の説明・検証に使う。

## 3. Tick実行順序との関係

因果Logと神託Debugは、固定tick実行順序の後半に接続する。

推奨位置:

```text
権能候補収集
祝詞条件判定
候補評価
結界Lock予約
天津裁定
神意確定
Motion / Battle / Asset などの処理実行
世界状態反映
言霊Event発行
因果Log記録
神託Debug出力
```

因果Logは、状態反映とEvent発行の後に、理由と結果を記録する。
神託Debugは、候補選択・条件判定・評価・裁定・実行結果を開発者が追える形で出力する。

## 4. 権能ライフサイクルとの関係

権能ライフサイクルでは、以下の段階が因果Log / 神託Debugに接続する。

```text
発見:
  候補として見つかった権能をDebugへ残す

条件判定:
  条件を満たした/満たさなかった理由をDebugへ残す

評価:
  評価値と評価理由をDebugへ残す

予約:
  結界Lockの成功/失敗をDebugへ残す

裁定:
  天津裁定の勝敗と理由をDebugへ残す

実行:
  使われた権能と対象を因果Logへ残す

結果反映:
  変化した世界状態を因果Logへ残す

言霊Event発行:
  発行されたEventを因果Logへ関連付ける
```

## 5. 因果Logの最小記録項目

最小の因果Logには、以下を記録する。

```text
因果Id
Tick
種類
概要
実行者Entity
対象Entity / 対象Asset / 対象場所
反応した偏差
使用された権能
参照した常態核
発行された言霊Event
変化した世界状態
関連する因果Id
```

v0.1最小では、さらに絞って以下だけでもよい。

```text
Tick
概要
実行者
対象
変化した値
発行Event
```

例:

```text
Tick: 120
概要: 祠が祓われた
実行者: player
対象: 荒れた祠
変化: 穢れ -30
発行Event: 祓い成功
```

## 6. 因果Logに残すべき理由

因果Logに残すべき理由情報:

```text
どの偏差に反応したか
どの権能が使われたか
なぜその権能が選ばれたか
どの常態核に基づいたか
どのEntityやAssetに影響したか
その結果、世界状態がどう変わったか
```

例:

```text
村人が祠で祈った理由:
- 村の穢れ偏差が高い
- 祠に「祈る」権能がある
- 村人は祠を観測済み
- 村人と祠に縁がある
- 畑の収穫より祈祷の評価が高かった
- 神意が祈祷を選んだ
```

## 7. 神託Debugの最小出力項目

神託Debugには、開発者が判断理由を追うための情報を出す。

最小出力候補:

```text
Tick
対象Entity
検出された偏差
候補権能一覧
条件判定結果
候補ごとの評価値
候補ごとの評価理由
結界Lock結果
天津裁定結果
選ばれた神意
却下された候補
却下理由
発行された言霊Event
関連する因果Log
```

v0.1最小では、以下だけでもよい。

```text
Tick
対象Entity
候補権能一覧
選ばれた権能
却下理由
発行Event
```

## 8. 神託Debugで説明すべきこと

以下を説明できるようにする。

```text
なぜこの行動を選んだか
なぜ他の行動を捨てたか
どの偏差が効いたか
どの権能が候補にあったか
どの祝詞条件で弾かれたか
どの結界Lockで失敗したか
どの因果が判断に影響したか
どの裁定規則で勝敗が決まったか
```

神託Debugは、ゲーム内世界の正式な履歴ではない。
開発者向けの説明出力である。

## 9. 因果Logと神託Debugの保存方針

初期段階では、因果Logと神託Debugを同じものにしない。

```text
因果Log:
  世界の履歴として残る。
  将来的にセーブ、リプレイ、物語、NPC記憶へ使う。

神託Debug:
  開発者向けの説明。
  必ずしもセーブ対象ではない。
  表示量が多くてもよいが、v0.1では最小にする。
```

初期実装時には、両者を同じデータから派生させてもよい。
ただし、概念上は分けて扱う。

## 10. 決定論

以下を原則とする。

```text
同じ初期状態、同じ入力列、同じSeedなら、同じ言霊Event列と因果Logを返す。
```

因果Logと神託Debugでは、特に以下に注意する。

```text
記録順を固定する
EntityId / AssetId で安定ソートする
候補権能の並び順を固定する
同点評価時のタイブレーク規則を残す
Set / Map / Dictionary の列挙順に依存しない
システム時刻をゲーム結果に混ぜない
外部環境により結果が変わらないようにする
```

神託Debugの表示順も、可能な限り決定論的にする。

## 11. v0.1で扱う範囲

現在のv0.1では、位置変更専用の既存因果台帳に加え、Entity位置変更と地盤振動発生を混在保存するインメモリの `統合因果台帳` を実装している。
統合Replayは位置変更結果、記録済みEvent、地盤振動の正式信号を同じ因果順から原子的に再構築するが、神託Debugはまだ実装しない。
位置変更記録へダミー信号を入れず、地盤振動記録へ対象Entityや変更前後位置を捏造しない。

v0.1現在の実装済み範囲:

```text

インメモリのイミュータブル因果台帳
入力順の原子的な一括追記
失敗記録と因果操作ID重複の拒否
Tick非減少順序の保証
変更前位置による分岐検出
Entity位置変更結果と記録済みEvent列の決定論的な再生
再生失敗時の初期状態への原子的復帰
正式因果ID、実行者ID、生成信号、Eventを保持する地盤振動発生記録
位置変更と地盤振動発生を判別共用体で保持する統合因果台帳
```

## 12. 実装段階候補

将来的な実装段階は以下を候補にする。

```text
Stage 1（実装済み）:
  因果台帳の最小型と原子的な追記を作る
  成功したEntity位置変更の記録候補だけを正式履歴へ変換する

Stage 2（結果再生まで実装済み）:
  因果台帳のEntity位置変更結果を変更前位置の検証付きで再適用する
  永続保存と完全な記紀Replayは後続とする

Stage 2.5（専用結果まで実装済み）:
  地盤振動発生の成功結果を専用記録として返す
  位置変更専用台帳へ偽装保存しない

Stage 2.6（統合結果再生まで実装済み）:
  位置変更と地盤振動発生を統合因果台帳へ保存する
  状態、Event、地盤振動信号を同一因果順から再構築する

Stage 3:
  神託Debugの最小型を作る
  Tick、候補、選択、却下理由だけを持つ

Stage 4:
  権能ライフサイクルの条件判定と評価に接続する

Stage 5:
  因果Logを御魂Stateやリプレイへ接続するか検討する

Stage 6:
  神託Debugを禊Reportや開示Viewへ接続する
```

ただし、一度に全部作らない。

## 14. まとめ

```text
言霊Event = 何が起きたか
因果Log = なぜ起きたか、何に影響したか
神託Debug = なぜその判断を選んだか
```

思兼神エンジンの世界AIは、常態、偏差、権能、祝詞、縁、観測、記憶、荒魂、禍津、穢れ、神意、天津裁定、結界Lockが絡む。

そのため、結果だけを見ても判断理由は分からない。
因果Logと神託Debugは、世界AIを信用できるものにするための最小補助仕様である。

最初から大きなログ基盤を作らず、まずはTick、概要、実行者、対象、発行Event程度の最小記録から始める。
