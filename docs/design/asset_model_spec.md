# Asset概念仕様書

## 1. 概要

思兼神エンジンでは、開発効率化と検証可能性を高めるために、以下の3種類のAsset概念を使い分ける。

```text
権能Asset = 能力・効果の部品
雛形Asset = Entity生成の設計図
派生Asset = 既存設計図との差分
```

この3つはすべて「再利用」のための仕組みだが、再利用する対象が違う。

```text
権能Asset = 何ができるか
雛形Asset = 何を持った存在として生成するか
派生Asset = 元から何を変えるか
```

## 2. 権能Asset

権能Assetは、ゲーム内の能力・効果・作用を表すAssetである。

対象例:

```text
- 体当たり攻撃
- 火炎弾
- 回復魔法
- 毒付与
- 死亡時爆発
- 地形ダメージ
- 召喚
- イベント発火
```

権能Assetは、キャラや敵そのものではない。
あくまで「能力」「効果」「作用」を定義する。

例:

```text
スライム = 敵Entity
体当たり攻撃 = 権能Asset
炎上付与 = 権能Asset
死亡時分裂 = 権能Asset
```

目的は、攻撃処理や効果処理を敵ごと・武器ごとに直接書かず、再利用可能な部品として扱うこと。

```text
権能Assetの問い:
このAssetは何ができるか？
```

## 3. 雛形Asset

雛形Assetは、Entityを生成するための基本設計図である。

対象例:

```text
- 敵
- 弾
- 宝箱
- 扉
- 採取ポイント
- UI部品
- ステージ部品
```

たとえば「スライム」を生成するには、HP、位置、速度、当たり判定、描画、AI、権能などが必要になる。
それらを毎回手で組むのではなく、雛形Assetとしてまとめる。

例:

```text
スライム雛形
  - HP成分
  - 位置成分
  - 速度成分
  - 当たり判定成分
  - 描画参照
  - 敵AI
  - 体当たり権能
  - Tag: 敵, 小型, 粘体系
```

目的は、Entity生成時の構成漏れや重複コードを減らすこと。

```text
雛形Assetの問い:
この存在は何を持って生成されるか？
```

## 4. 派生Asset

派生Assetは、既存の雛形AssetやAssetから差分だけを定義するAssetである。

対象例:

```text
- 火炎スライム
- 毒スライム
- 巨大スライム
- 高速スライム
- ボス版スライム
```

ゼロからすべて定義し直すのではなく、元のAssetとの差分だけを書く。

例:

```text
火炎スライム派生
  - 元Asset: スライム雛形
  - Tag追加: 火属性
  - 描画差し替え: fire_slime_sprite
  - 権能差し替え: 体当たり攻撃 -> 火属性体当たり
```

目的は、コピー地獄を防ぐこと。
元の定義を再利用しつつ、必要な違いだけを明示する。

```text
派生Assetの問い:
元Assetから何を変えるか？
```

## 5. 3つの関係

基本関係は以下。

```text
権能Asset
  ↓
雛形Assetが参照する

雛形Asset
  ↓
Entity生成に使う

派生Asset
  ↓
雛形Assetや権能Assetの差分変更に使う
```

例:

```text
権能Asset: 体当たり攻撃
  - 衝突時に10ダメージ

権能Asset: 火属性体当たり
  - 衝突時に12ダメージ
  - 炎上付与

雛形Asset: スライム
  - HP 30
  - 移動速度 1
  - 当たり判定 小
  - 描画 slime.png
  - 権能: 体当たり攻撃

派生Asset: 火炎スライム
  - 元Asset: スライム
  - Tag追加: 火属性
  - 描画変更: fire_slime.png
  - 権能差し替え: 体当たり攻撃 -> 火属性体当たり
```

解決後のEntity:

```text
火炎スライムEntity
  - HP 30
  - 移動速度 1
  - 当たり判定 小
  - 描画 fire_slime.png
  - Tag: 敵, 小型, 粘体系, 火属性
  - 権能: 火属性体当たり
```

## 6. 権能Assetと雛形Assetの違い

```text
権能Asset = 能力
雛形Asset = 存在の構成
```

例:

```text
火炎弾を撃つ
  -> 権能Asset

火炎弾を撃つ敵
  -> 雛形Asset
```

悪い設計:

```text
スライム雛形の中に体当たり処理を直接書く
```

良い設計:

```text
スライム雛形は体当たり権能Assetを参照する
```

こうすることで、同じ体当たり権能を別の敵にも使い回せる。

## 7. 雛形Assetと派生Assetの違い

```text
雛形Asset = 基本形
派生Asset = 基本形との差分
```

雛形Assetは単体でEntity生成に使える。

```text
スライム雛形
  -> スライムEntityを生成できる
```

派生Assetは、元Assetがないと意味を持たない。

```text
火炎スライム派生
  -> 元のスライム雛形が必要
```

派生Assetは完成品ではなく、変更指示書である。

```text
元を読む
差分を適用する
解決済みAssetを作る
検証する
Entityを生成する
```

## 8. AssetとStateの境界

Assetは定義・設計図であり、Stateは実行中の状態である。

```text
Asset = 設計図
State = 現在の実体
```

例:

```text
最大HP 30
  -> Asset

現在HP 18
  -> State

初期速度 1
  -> Asset

現在速度
  -> State

攻撃威力 12
  -> Asset

クールダウン残り20tick
  -> State
```

権能Asset、雛形Asset、派生Assetは、実行前の定義として扱う。
セーブ・復元される実行時状態は御魂State側で扱う。

## 9. 実装優先度

3つとも設計上は有用だが、実装順は分ける。

```text
v0.1: 権能Asset
v0.2: 雛形Asset
v0.3: 派生Asset
```

### v0.1: 権能Asset

最初に実装する。
理由は、攻撃・回復・状態異常・イベント発火など、ゲームルールの部品化に直結するため。

```text
採用確定
最優先で堅く作る
```

### v0.2: 雛形Asset

次に実装する。
敵、弾、宝箱、扉、UI部品など、Entity生成が増えてきた段階で必要になる。

```text
採用予定
Entity量産が始まったら実装する
```

### v0.3: 派生Asset

後回しでよい。
敵や武器のバリエーションが増え、コピー地獄が見えてきたら実装する。

```text
概念だけ確保
実装は後回し
```

## 10. 派生Assetの注意点

派生Assetは便利だが、継承を深くしすぎると最終値が分からなくなる。

危険な例:

```text
スライム
  ↓
火炎スライム
  ↓
巨大火炎スライム
  ↓
高速巨大火炎スライム
```

初期ルールとしては、以下を推奨する。

```text
- 派生は1段階まで
- 派生Assetを元にした派生Assetは禁止
- 循環参照は禁止
- 差分適用後は必ず検証する
- 解決済みAssetをログで確認できるようにする
```

最初は自由度よりも安全性を優先する。

## 12. 実行時の流れ

派生Assetを使う場合の流れ。

```text
派生Assetを読む
  ↓
元の雛形Assetを読む
  ↓
差分を適用する
  ↓
参照している権能Assetを読む
  ↓
解決済みAssetを作る
  ↓
禊Testで検証する
  ↓
Entityを生成する
  ↓
思兼神Coreの固定tick上で実行する
```

## 13. 最終判断

現時点の方針は以下。

```text
権能Asset:
  採用確定。
  最初に堅く作る。

雛形Asset:
  採用予定。
  敵・弾・オブジェクトの量産が始まったら追加する。

派生Asset:
  概念だけ確保。
  複製地獄が見えてから実装する。
```

短くまとめると、以下。

```text
権能Assetは、ゲームルールを部品化する。
雛形Assetは、Entity生成を部品化する。
派生Assetは、バリエーション制作を部品化する。
```

この3つを段階的に入れることで、思兼神エンジンは「毎回コードを書く」方式から、「検証済みの部品を組み合わせる」方式へ進める。
