# ADR-021: 行動候補の最小選択は最高優先度と入力順タイブレークを使う

- Status: Accepted
- Date: 2026-08-11

## Context

行動候補生成までは存在するが、同一主体について生じた複数候補から一件を選ぶ境界がなかった。
候補選択から直接ゲーム状態を変更すると、判断、実行、因果操作化の責務が混ざる。
ランダムな選択や非安定な列挙順による同率選択は決定論を壊す。
現在の候補種別は `その場警戒` だけだが、異なる仮説から複数候補が生じ得る。

## Decision

- 選択APIは同一主体の候補一覧だけを扱う。
- 空一覧は正常な候補なしとして `Ok None` を返す。
- 全候補を入力順で防御的に検証する。
- 行動候補IDは一覧内で一意とする。
- 妥当な候補のうち最高優先度の候補を一件選ぶ。
- 同率最高時は入力順で最初の候補を選ぶ。
- 候補ID、仮説、種別をタイブレークに使わない。
- 選択済み値は候補一覧、選択位置、選択候補を保持する。
- 選択済み値をprivate表現とし、不正な選択を外部から構築させない。
- 候補選択と実行、因果操作化、Event発行を分離する。

## Consequences

- 同じ候補一覧から構造的に同じ選択結果を得られる。
- 選択理由、同率最高候補、非選択候補を入力順のまま追跡できる。
- 呼び出し側はDictionaryやHashSetの非安定な列挙順ではなく、安定した候補入力順を供給する必要がある。
- 複数主体一括選択、ヒステリシス、cooldown、種別補正、候補実行は後続となる。

## Implementation Status

実装済み:

- `行動候補選択.選ぶ` による同一主体の決定論的な一件選択
- 候補全件検証、実行者境界、候補ID一意性
- 最高優先度と入力順タイブレーク
- privateな `選択済み行動候補` と説明用アクセサ
- 因果認識閉ループと統合Replayから生成した候補の選択検証
- 選択済み値から意味的なエンティティ反応要求を作り、選択理由と却下候補を保持する下流接続
- 反応要求から因果操作、反応状態、統合台帳、Replayへ由来を保って接続する下流経路

未実装:

- 複数主体の一括選択
- 複数の行動候補種別と種別補正
- ヒステリシス、cooldown、継続意図
- 反応状態のMovement解釈、解除、複数要求の競合裁定
